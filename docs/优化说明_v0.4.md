# 优化说明 v0.3 → v0.4（中期答辩版）

> 优化日期：2026-10-19 · 对齐目标：国家级大创中期检查
> 一句话总结：**修好了检索底座（中文嵌入 + BM25 + RRF），给核算加上不确定性区间，修了 6 个会在答辩现场出问题的 Bug，并把“可信度证据”做进前端。** 119 项测试全部通过。

## 1. 底层架构：RAG 检索重构

### 1.1 发现的核心问题
v0.3 报告中“纯向量组 MRR 0.04”被解释为“向量检索不适合政策文本”。**这个结论是错的。** 实际原因是 `chromadb-default` 背后是英文模型 all-MiniLM-L6-v2，对中文几乎没有语义区分能力。如果答辩时评委追问这一点，原来的结论站不住。

### 1.2 新架构
```
query ──┬── BM25（jieba 分词 + 60 个碳市场/交通领域词 + 停用词）  ──┐
        ├── 稠密向量（bge-small-zh-v1.5，BGE 官方查询指令前缀）    ──┼── RRF 融合(k=60) ──[可选 bge-reranker 精排]── Top-K
        └── v0.3 字面规则打分（降级为其中一路信号）               ──┘
```
| 新文件 | 作用 |
|---|---|
| `src/rag/embeddings.py` | 嵌入适配层：`auto` / `fastembed:*` / `chromadb-default` / `openai:*`；缺依赖时自动降级并给出提示 |
| `src/rag/bm25.py` | 中文 Okapi BM25 和 RRF（Cormack 等，SIGIR 2009），没有引入额外依赖 |
| `src/rag/reranker.py` | 可选的交叉编码器精排，默认关闭，用 `RERANKER_MODEL` 开启 |
| `src/rag/vector_store.py` | 重写。一共 7 种检索模式，旧的 `hybrid` 原样保留，方便复现 v0.3 |

**为什么默认用三路 RRF（rrf3）：**

- RRF 只看名次，不依赖各检索器分数的量纲，所以**不用在评测集上调权重**。k=60 是原论文的推荐值。
- v0.3 字面规则里有几条是“看过评测题之后写的”主题加权（例如“问题含‘试点’且来源含‘北京’就加 0.20”），有过拟合风险。v0.4 只让它作为三路之一参与融合，不再让它主导打分。

### 1.3 工程层面
- **进程级单例**：`get_vector_store()`。v0.3 每次请求都会新建向量库对象、重新加载模型；现在模型和 BM25 索引只加载一次。
- **入库幂等**：同名文档先删后写，避免文档变短后残留“幽灵块”。新增批量接口 `/api/kb/ingest-all`。
- **启动自动建库**：设置 `KB_AUTO_INGEST=1`（Compose 默认开启），首次部署不用再手动跑脚本。
- **证据溯源**：`/api/ask` 的每条来源现在都带 `chunk_id`、原文摘录、命中的检索器，以及接口耗时 `latency_ms`。

## 2. 核算引擎

### 2.1 新增：蒙特卡洛不确定性分析（`src/engine/uncertainty.py`，`POST /api/uncertainty`）
依据 IPCC 2006 第 1 卷第 3 章的 Approach 2：

- **排放因子**：自动收集因子库里同一车型的多个来源取值（《中国环境科学》2021、GB 30510-2024/2018、实测值），构成三角分布 Tri(min, 基准值, max)，相对半宽不低于 10%。
- **年均里程**：正态分布，变异系数按数据质量取值：台账 5%、抽样 10%、估计 20%。
- **满载率**：U(l±0.05)。
- **输出**：P5/P50/P95、相对不确定度，以及 Spearman ρ² 归一化后的方差贡献，用来回答“企业应该先改进哪项数据”。
- 固定随机种子，结果可复现；1 万次抽样约 20 ms。

**一个可以在答辩中讲的发现**：车队里有 LNG 重卡时，抽样均值比点估计偏高约 2%。原因是 LNG 实测值（0.94–1.20 kg/km）普遍高于指南值 0.72，分布右偏，说明**只给点估计会系统性低估排放**。

### 2.2 Bug 修复
| 问题 | 影响 | 修复 |
|---|---|---|
| 同一车型录入多组不同满载率时，“满载率调整系数”被后一组覆盖 | 明细表显示错误 | 改为全精度聚合，系数按车公里加权；新增“车公里_万km”列 |
| 逐组先四舍五入再累加 | 大车队有舍入误差 | 改为最后统一舍入 |
| CSV 中 LNG“实测高值”=0.94、“实测低值”=1.20，标签写反了 | 数据可信度 | 已对调（v0.3 的 code review 曾指出过） |

## 4. 会在答辩现场出问题的 Bug（已修）

1. **PDF 报告中文变方框（Linux/Docker）**：字体候选列表末尾的 `DejaVuSans.ttf` 不含中文字形，却能“注册成功”。已删除这一项，并用 reportlab 内置的 `STSong-Light` CID 字体兜底，任何系统都能正常显示中文。
2. **前端在代理环境下请求 404**：校园网、Clash 等全局代理会把 `localhost` 请求转发出去。现在本机和 Compose 内网地址会绕过系统代理。
3. **环境变量为空字符串时地址丢失**：`API_BASE_URL=`（Compose 常见写法）会让前端请求相对路径。现在所有关键变量为空时都会回退到默认值。
4. `charts.py` 使用了 `Optional` 却没有导入，只是因为 `from __future__ import annotations` 才没报错，换个用法就会崩。已修复。
5. 测试依赖本地知识库状态：库里不是完整的 268 块时，2 项基准测试会失败。现在入库脚本支持 `--force` 全量重建，CI 也会先建库。
6. API 端点原来是 `async def`，里面却在做同步的 CPU/IO 计算，会阻塞事件循环。已改为同步端点，由 FastAPI 线程池执行。另外 API Key 比较改为常量时间比较（`secrets.compare_digest`）。

另外新增请求中间件：每个请求都带 `X-Request-ID` 和 `X-Process-Time-ms`，并写入结构化日志。

## 6. 检索实验完整结果（40 题金标集，268 块）

| 方案 | MRR [95% CI] | R@1 | R@3 | R@5 | R@10 | nDCG@10 |
|---|---|:---:|:---:|:---:|:---:|:---:|
| A 字面启发式(v0.3) | 0.488 [0.35, 0.63] | 40.0% | 52.5% | 67.5% | 70.0% | 0.452 |
| B 纯稠密向量(bge-zh) | 0.272 [0.17, 0.38] | 12.5% | 37.5% | 47.5% | 57.5% | 0.296 |
| C 加权重排(v0.3 默认) | 0.490 [0.36, 0.62] | 37.5% | 55.0% | 67.5% | 72.5% | 0.463 |
| D BM25(jieba) | 0.440 [0.32, 0.57] | 30.0% | 55.0% | 60.0% | 70.0% | 0.439 |
| E BM25+向量 RRF | 0.338 [0.24, 0.44] | 15.0% | 50.0% | 60.0% | 72.5% | 0.380 |
| **F 三路 RRF(v0.4 默认)** | **0.433** [0.32, 0.55] | 27.5% | 47.5% | **67.5%** | **80.0%** | 0.446 |
| F + bge-reranker 精排 | 0.365 | 22.5% | — | — | 70.0% | — |

**答辩时请如实讲这三点（评委更看重诚实的消融，而不是好看的数字）：**

1. F 组的优势在**召回**：Recall@10 最高，Recall@5 并列最高（生成回答时取 top-5 给大模型）。它的 MRR 和 v0.3 加权重排相比没有显著差异（Holm 校正后 p=1.0），**不要说“全面超越”**。
2. 两路 RRF（E 组）的 MRR 反而低于 BM25 单路。原因是稠密向量对“情景描述型”长问题仍然偏弱。这是下一阶段的研究点：查询改写或问题分解，换更大的中文嵌入模型。
3. 交叉编码器精排在 CPU 上约 9 秒一题，指标还下降了，所以默认关闭。这是负面结果，照实说。

复现：`python scripts/ingest_policy_docs.py --force && python scripts/evaluate_rag_benchmark.py --embedding-ablation`
完整报告：`docs/rag_benchmark/rag_retrieval_experiment_report.md`
