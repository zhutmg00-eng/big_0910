# 迭代队列（对标国家级大创）

本文件是持续迭代的待办台账。每条都写清**证据**（问题在哪、怎么验证），
避免「感觉可以更好」式的改动。完成一条就把状态改为「已完成」并保留原文。

约定：
- 每条改动必须能由 `python -m pytest -q` + `ruff check src tests scripts` 验证；
- 涉及对外数字的改动，必须同时更新台账（`docs/derived_metrics.json`）或实测结果 JSON，
  不能只改文档；
- 一次提交只做一条，便于 `git bisect` 定位。

## I-1 死代码：`src/rag/crawler.py` 与 `src/models/carbon.py` 无人引用

- **证据**：`grep -rn "crawler\|models.carbon" --include=*.py src scripts tests` 除自身外无命中；
  `docs/architecture.md:50` 仍在目录说明里写「crawler.py — 政策文档爬取」。
- **风险**：README 未提爬虫，但架构文档列了它，评审按文档读代码会找不到调用链。
- **做法**：二选一——(a) 删除并在架构文档移除该行；(b) 保留但在模块 docstring
  标注「未接入主流程，留作扩展」。优先 (a)，除非爬虫有独立价值。
- **状态**：已完成（2026-10-27，提交 `2e59ad3`）——两个文件都删除。`crawler.py`
  除零引用外还内置浏览器 UA 伪装且不检查 robots.txt，保留即是合规隐患；
  `carbon.py` 的字段与 `engine/calculator.py` 的 dataclass 重复。顺带发现
  `src/ui/pages/` 是只有 0 字节 `__init__.py` 的空包，一并删除。
  新增 `tests/test_module_reachability.py` 做 AST 可达性遍历，防止再积死代码。

## I-5 案例外部效度（GAP-4）缺「小样本无台账」场景验证

- **证据**：`docs/known_gaps.md` GAP-4 自陈验证集是「有台账的头部企业」，
  而目标用户是「无台账的中小车队」，两者不是同一群体。
- **做法**：构造 1–2 个合成的小车队场景（10–50 辆，车型混合、里程区间宽），
  跑敏感性分析说明在无台账条件下的误差包络；不做「准确率」声明，只给区间。
- **状态**：已完成（2026-10-27）——新增 `scripts/small_fleet_envelope.py` 与
  `docs/small_fleet_envelope.md`，4 个画像（20/35/12/50 辆）。包络 −26%~+29%；
  因数分解显示里程单独 ±25%、满载率单独 2.6–3.0%（LF 值域 [1,1.1125] 的解析上界
  是 +11.25%/−10.1%）；误差预算显示要控在 ±10% 内里程需准到 ±6%~±7%。
  `docs/known_gaps.md` GAP-4 与 README 均已补这条定量回应。
  守卫 `tests/test_small_fleet_envelope.py` 用引擎复算包络、验证里程效应的线性、
  校验 LF 解析上界与误差预算，并拦截「把包络当准确率」与「引用分位数」两种误用。

## I-6 生成层无引用准确率评测

- **证据**：RQ2 只评检索（MRR/Recall），报告第五节自陈「下一步加入生成质量评测
  （忠实度、引用准确率）」，目前未实现。
- **做法**：给定检索结果后，校验回答中出现的每一条「条款名 + 数字」能否在
  检索到的 chunk 里逐字找到；无 LLM 时用检索式回答即可跑，属于可离线验证的指标。
- **状态**：已完成（2026-10-27）——新增 `scripts/evaluate_answer_grounding.py`，
  三项指标：引用文件名可溯源率、数值可溯源率、单位最长匹配。40 题实测
  引用 75/75、数值 237/237，均为 100%。**该 100% 在未配置 LLM 时按构造成立**
  （回答由逐字摘录生成），已在 README 与 known_gaps 中写明，不冒充忠实度证据。
  开发过程修了三个检查器自身的真实缺陷：① 引文正则允许跨行，把
  「2026 年度碳…
- 《…》」拼成假文件名（Q02）；② 把回显的用户问题当系统断言，
  Q33 的「运距约700公里」被误判编造；③ 单位交替顺序导致「亿吨」被截成「亿」。
  守卫 `tests/test_answer_grounding.py` 以负例为主：伪造文件名、伪造数值、
  跨行假引用、回显问题、千分位写法，五条对照确保检查器不是永远返回 100% 的空壳。

## I-8 测试之间互相污染（AppTest 同进程全局赋值）

- **证据**：`tests/test_ui_views_render.py` 单独跑 `-k` 通过、成组跑失败。
  根因：AppTest bare 模式**在同一进程**执行脚本，脚本里写的
  `val.RAG_RESULTS = ...`、`adv.api_post = ...` 是真实模块的全局赋值，
  执行完不还原，后续测试拿到上一个测试的残留状态。
- **做法**：一律改为在测试函数里用 `monkeypatch.setattr` 修改并在
  teardown 自动还原；政策顾问页再加一个 autouse fixture 默认把后端置为
  「连接失败」，防止任何测试意外打到真实 8000 端口。
- **状态**：已完成（2026-10-27）——`test_ui_views_render.py` 全量改写的同一提交。

## I-9 RQ2 只有总体指标，缺分层评测

- **证据**：`rag_retrieval_experiment_results.json` 里 `detailed_results` 有
  每题的 `type` / `difficulty`，但 `summarize()` 只算 40 题总体，报告与
  README 从未给出分题型/分难度读数。报告第五节自己也写着「下一步按分层评测」。
- **发现（分层后暴露的真实反常）**：标为「中」的题 MRR 0.326 低于标为
  「难」的题 0.475。原因是难度按**人工阅读理解难度**标注，不是按检索难度；
  「中」档含多道跨文件对比题（购电口径、三地试点），对检索更难；
  「难」档有若干问句与条款用词高度重合的题，反而容易命中。
- **做法**：`stratified()` 按 `type` 与 `difficulty` 各出一张含 CI 的表；
  报告新增三·三节，并由脚本自动检出上述不一致、插入警示语。
- **状态**：已完成（2026-10-27）。守卫 `tests/test_rag_negative_suite.py::
  TestStratifiedMetrics` 校验分层题数合计=40、MRR 落在置信区间内、
  反常存在时报告必须写明「不能当能力证据」。
